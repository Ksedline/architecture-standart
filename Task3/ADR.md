### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | Доступность сервисов не ниже 99,9% (см. R1, R2 FURPS+). |
| 2 | Отказоустойчивость: два ЦОД, масштабирование фронта и сервисов (см. R1, S3). |
| 3 | Быстрый отклик: UI ≤ 200 мс, расчёт ставки ≤ 100 мс (см. U2, P1, P2). |
| 4 | Весь трафик шифруется (TLS 1.2+), секреты — в защищённом хранилище. |
| 5 | Прямых интеграций между интернет-банком и АБС не допускается — только через отдельный сервис или очередь. |
| 6 | Для SMS-подтверждений реализуется отдельный сервис OTP, чтобы не дорабатывать ядро ИБ. |
| 7 | Используются только технологии, поддерживаемые IT-ландшафтом банка (Java, .NET, MS SQL, Oracle и др.). |
| 8 | Вся архитектура и API документируются, настраиваются CI/CD пайплайны. |
| 9 | Для защиты АБС от перегрузки — кэширование, троттлинг, circuit-breaker. |

### <a name="_qmphm5d6rvi3"></a>**Решение**

**Диаграммы:**
- [C4 Context](C4_Context.puml)
- [C4 Container](C4_Container.puml)

**Основные компоненты и интеграции:**
- Website FE/BE — публичный сайт, каталог депозитов, форма заявки (Web-разработчики)
- Интернет-банк — личный кабинет клиента, интеграция с API (Команда ИБ)
- API Gateway / MQ — единая точка входа, маршрутизация событий (DevOps/Интеграция)
- Deposit Gateway — оркестрация заявок, взаимодействие с АБС (Core Transformation)
- Rate Service — расчёт и хранение ставок, кэширование (Core Transformation)
- OTP Service — генерация и проверка SMS-кодов (Инфраструктура/Безопасность)
- Call-center Platform — работа с лидами, интерфейс операторов (IT кол-центра)
- АБС — учёт депозитов, ставки, операции (Команда АБС)
- SMS-Gateway — отправка SMS (Инфраструктура)

**Логика выбора решений:**
- Внешние обращения проходят через API Gateway или очередь сообщений для гибкости и отказоустойчивости.
- Для расчёта ставок и работы с заявками используются отдельные микросервисы, чтобы минимизировать изменения в существующих системах.
- Для подтверждения операций реализуется собственный сервис OTP, что снижает зависимость от подрядчика.
- В качестве брокера сообщений на MVP используется RabbitMQ, с возможностью перехода на Kafka в будущем.
- Кэширование ставок и read-only интеграция с АБС позволяют обеспечить быстрый отклик и снизить нагрузку на основную систему.
- Все требования FURPS+ учтены в архитектуре и интеграциях.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

- Прямые REST-запросы из ИБ в АБС: быстро реализуется, но нарушает требования по отказоустойчивости и безопасности, создаёт риск перегрузки АБС.
- Хранить ставки только в АБС: нет дублирования данных, но время отклика увеличивается, нагрузка на АБС возрастает.
- Внедрять весь функционал депозитов в ядро ИБ: не нужно создавать новые сервисы, но монолит сложно масштабировать, затруднена интеграция с современными решениями.

**Недостатки, ограничения, риски**
- Текущая архитектура интернет-банка (ASP.NET 4.5) затрудняет быстрые изменения и масштабирование.
- АБС поддерживает только вертикальное масштабирование, что ограничивает обработку большого потока онлайн-заявок.
- RabbitMQ выбран как временное решение — при переходе на Kafka потребуется миграция.
- Реализация собственного OTP-сервиса требует времени на интеграцию с HSM и сертификацию.
- Возможна перегрузка команды трансформации из-за необходимости разработки новых сервисов и интеграций.
- Если ручная обработка заявок в бэк-офисе будет занимать много времени, это негативно скажется на клиентском опыте.
