## <a name="_3bfxc9a45514"></a>**Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
|:-:|------------------------------|----------|----------|
| 1 | Гость сайта                  | Просмотреть линейку депозитов | Клиент заходит на сайт и видит актуальные депозитные продукты с текущими ставками. |
| 2 | Гость сайта                  | Оставить заявку на депозит     | Клиент заполняет форму с ФИО и телефоном. Заявка передаётся в систему кол-центра через очередь сообщений. |
| 3 | Оператор кол-центра          | Позвонить клиенту и уточнить детали | Оператор получает заявку, связывается с клиентом, может предложить персональную ставку. |
| 4 | Идентифицированный клиент (ИБ) | Рассчитать персональную ставку | В интернет-банке клиент видит персонализированные ставки, основанные на его профиле и истории. |
| 5 | Идентифицированный клиент (ИБ) | Подать заявку на депозит        | Клиент указывает счёт и сумму депозита, подтверждает операцию одноразовым SMS-кодом. |
| 6 | Бэк-офис депозитов           | Обработать заявку               | Менеджер бэк-офиса обрабатывает заявку вручную, согласует ставку при необходимости и регистрирует депозит в АБС. |
| 7 | Система                      | Информировать клиента          | После успешного открытия депозита клиент получает SMS-уведомление о статусе. |

## <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

| № | Требование |
|:-:|------------|
| 1 | Доступность сервисов ≥ 99.9% (R-1, R-2). |
| 2 | Отказоустойчивость через два ЦОД, горизонтальное масштабирование фронтов и микросервисов (R-1, R-2, S-4). |
| 3 | Время отклика UI ≤ 200 мс; генерация ставки ≤ 100 мс (U-2, P-1). |
| 4 | Все каналы шифруются TLS 1.2+, секреты хранятся в Vault (+R-2). |
| 5 | Интеграция между интернет-каналами и АБС только через прослойку (API-Gateway / Integration Bus), без прямых вызовов (+R-1, +R-4). |
| 6 | Реализовать собственный OTP Service (HTTP+HSM), чтобы избежать доработок ядра интернет-банка (F-4). |
| 7 | Использовать существующие технологии банка: Java 17 / Spring Boot, .NET 4.5, MS SQL / Oracle (S-3). |
| 8 | Настроить CI/CD пайплайны и предоставить Swagger-документацию (S-2, S-1). |
| 9 | Ограничить нагрузку на АБС — использовать кэширование, circuit-breaker и троттлинг (+R-4). |

#### Основные компоненты и интеграции

| Компонент | Назначение | Владелец / ответственная команда |
|---------|------------|----------------------------------|
| **Website FE/BE** | Публичный каталог депозитов и форма заявки | Web-team |
| **Интернет-банк** | Личный кабинет клиента, адаптированный для новых API | Команда интернет-банка |
| **API-Gateway / MQ** | Единая точка входа для внешних запросов, маршрутизация событий | DevOps / Integration-team |
| **Deposit Gateway** | Оркестрация заявок, запись в АБС, отправка событий | Core Transformation team |
| **Rate Service** | Расчёт и кэширование ставок, обращение к АБС только на чтение | Core Transformation team |
| **OTP Service** | Генерация и проверка SMS-кодов | Infrastructure / Security |
| **Call-center Platform** | Получение лидов, UI для операторов | IT-команда кол-центра |
| **АБС** | Главная система учёта депозитов | АБС-team |
| **SMS-Gateway** | Отправка SMS-уведомлений | Infra-team |

#### Логика выбора архитектурных решений:

- **Интеграция через очередь сообщений** обеспечивает защиту от пиковой нагрузки на АБС и повышает отказоустойчивость (NFR #5, #9).
- **Микросервисы вокруг депозитов** позволяют минимизировать изменения в старых системах (соответствие NFR #7).
- **OTP Service** позволяет снизить зависимость от подрядчика и улучшить безопасность.
- **RabbitMQ** выбран как временное решение для очередей, что даёт возможность быстро реализовать MVP с возможностью последующего перехода на Kafka (NFR #9).

#### Как удовлетворены требования:
- SLA по доступности реализуется через кластеры API-Gateway, RabbitMQ и микросервисов в двух ЦОД (NFR #1).
- Высокая производительность достигается кэшированием ставок (Redis) и read-only обращением к АБС (NFR #3).
- Безопасность обеспечивается использованием TLS для всего трафика и хранением секретов в HashiCorp Vault (NFR #4).
- Поддерживаемость повышена благодаря OpenAPI-документации и автоматизированным пайплайнам CI/CD (NFR #8).

## <a name="_bjrr7veeh80c"></a>**Альтернативы**

| Вариант | Плюсы | Минусы / причины отказа |
|--------|-------|--------------------------|
| Прямые REST-вызовы ИБ → АБС | Быстрая реализация | Нарушает NFR #5, создаёт риск перегрузки АБС и потери отказоустойчивости |
| Хранение ставок только в АБС без Rate Service | Отсутствие дублирования данных | Увеличивает нагрузку на АБС, время ответа не соответствует NFR #3 |
| Добавление функционала депозитов прямо в ядро интернет-банка | Не нужно создавать новые микросервисы | ASP.NET 4.5 — монолит, трудно масштабируется и развивается, блокирует стратегию с Kafka |

---

## **Недостатки, ограничения, риски**

- **Технический долг интернет-банка (ASP.NET 4.5)**: сложности с обновлением и расширением требуют долгосрочной стратегии.
- **АБС с вертикальным масштабированием**: при увеличении числа онлайн-заявок возможен bottleneck; используются троттлинг и кэширование, но риск остаётся.
- **RabbitMQ как временный брокер**: при переходе на Kafka потребуется миграция конфигураций и клиентов.
- **OTP Service**: интеграция HSM и сертификация могут затянуть сроки реализации.
- **Загрузка команды Core Transformation**: разработка новых микросервисов и шлюза требует дополнительных навыков DevOps/SRE.
- **Бизнес-риск ручной обработки**: если этап обработки заявки в бэк-офисе слишком долгий, клиенты могут воспринять сервис как медленный.
