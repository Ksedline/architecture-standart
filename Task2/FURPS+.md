# FURPS+ Матрица для цифровизации депозитного направления банка «Стандарт»

| Код | Требования                                                                                             | Комментарий |
|-----|----------------------------------------------------------------------------------------------------------|-------------|
| **F — Функциональные (Functionality)**                                                                     |             |
| F1  | Подача клиентом заявки на депозит на сайте, с указанием ФИО и телефона                                   | Персональные данные должны передаваться по защищённому каналу TLS. Архитектурно значимо |
| F2  | Реализация списка доступных депозитов и персонализированных ставок в Интернет-Банке                        | Ставки должны храниться в едином источнике данных. Архитектурно значимо |
| F3  | Подача клиентом заявки на депозит в интернет-банке, с указанием счёта и суммы                              | Требуется подтверждение через SMS (OTP). Избегать доработок ядра системы |
| F4  | Подтверждение заявки на депозит / согласование ставки менеджером бэк-офиса в АБС                           | Ручная обработка на этапе MVP. Интеграция должна быть через промежуточный сервис |
| F5  | Отправка SMS-уведомления клиенту о подтверждении ставки и открытии депозита                               | Использовать существующий SMS-шлюз. Не модифицировать ядро системы |
| F6  | Автоматизация расчета персонализированных ставок вместо Excel                                             | Защита от человеческой ошибки и ускорение обработки заявок. Архитектурно значимо |
|     |                                                                                                          |             |
| **U — Удобство использования (Usability)**                                                                 |             |
| U1  | Интерфейсы соответствуют принятой системе дизайна приложений                                              | Брендирование, консистентность UI/UX |
| U2  | Время загрузки экранов должно быть не более 1 секунды                                                     | Требует CDN, кэширования, read-replica баз данных. Архитектурно значимо |
| U3  | Адаптивная верстка для desktop, tablet, mobile                                                          | Для удобства пользователей всех устройств |
| U4  | Отображение статуса заявки клиенту                                                                       | Поскольку процесс не мгновенный, важно информировать клиента. Архитектурно значимо |
|     |                                                                                                          |             |
| **R — Надёжность (Reliability)**                                                                           |             |
| R1  | Доступность интернет-банка не ниже 99.9%, работа 24/7                                                    | Требуется распределение нагрузки между ЦОДами. Архитектурно значимо |
| R2  | Интернет-банк и АБС не должны взаимодействовать напрямую                                                  | Использовать шину сообщений или очередь. Архитектурно значимо |
| R3  | При недоступности АБС заявки надёжно ставятся в очередь и обрабатываются после восстановления              | Требуется механизм retry и отказоустойчивое хранение. Архитектурно значимо |
| R4  | SMS-сервис должен быть доступен не менее чем на 99.95%                                                   | Критично для завершения транзакций. Архитектурно значимо |
|     |                                                                                                          |             |
| **P — Производительность (Performance)**                                                                   |             |
| P1  | Время отклика операций в интерфейсе — миллисекунды                                                      | Требует оптимизации фронтенда и backend. Архитектурно значимо |
| P2  | Генерация персональной ставки занимает не более 100 мс                                                   | Требует in-memory кэша и асинхронного обновления. Архитектурно значимо |
| P3  | Система обрабатывает ≥ 50 заявок/сек без деградации                                                      | Определяет параметры стресс-тестирования. Архитектурно значимо |
| P4  | Шифрование не увеличивает 95-й перцентиль задержки более чем на 50 мс                                     | Рекомендовано TLS offload на уровне балансировщика |
|     |                                                                                                          |             |
| **S — Поддерживаемость (Supportability)**                                                                  |             |
| S1  | Используются только технологии, совместимые с IT-ландшафтом банка                                        | Java, .NET, PHP, MS SQL, Oracle, Kafka (перспективно) |
| S2  | Разработана документация для будущего расширения системы                                                 | Важно для CI/CD и DevOps. Архитектурно значимо |
| S3  | Горизонтальное масштабирование и контейнеризация                                                        | Kubernetes / Openshift. Архитектурно значимо |
| S4  | Поддержка CI/CD пайплайнов с авто-тестами                                                                | Влияет на инфраструктуру и процессы разработки. Архитектурно значимо |
|     |                                                                                                          |             |
| **+R — Ограничения (Restrictions)**                                                                        |             |
| +R1 | Интернет-банк должен быть подготовлен к масштабированию                                                  | Переход к микросервисной архитектуре. Архитектурно значимо |
| +R2 | Все данные клиента и передача информации должны быть защищены                                            | Соответствие законодательству РФ (152-ФЗ). Архитектурно значимо |
| +R3 | Текущая платформа интернет-банка несовместима с Kafka                                                    | Пока использовать REST или внутренние очереди. Архитектурно значимо |
| +R4 | АБС поддерживает только вертикальное масштабирование                                                     | Требуется троттлинг и кэширование. Архитектурно значимо |
| +R5 | Использовать только лицензионные СУБД (MS SQL, Oracle)                                                  | Исключение open-source решений, кроме кэшей и очередей |
| +R6 | SMS отправляются через существующий шлюз, без изменения ядра интернет-банка                               | Минимизация рисков и доработок со стороны подрядчика |
